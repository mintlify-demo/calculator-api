v1 shipped first with one endpoint per operation. v2 added a single, more flexible endpoint. Here is the same job in both.

<Tabs>
  <Tab title="v1: two numbers">
    ```bash
    curl -X POST http://localhost:8000/v1/multiply \
      -H "Content-Type: application/json" \
      -d '{"a": 6, "b": 7}'
    ```

    ```json
    { "result": 42 }
    ```
  </Tab>
  <Tab title="v2: any number of operands">
    ```bash
    curl -X POST http://localhost:8000/v2/calculate \
      -H "Content-Type: application/json" \
      -d '{"operation": "multiply", "operands": [6, 7, 2]}'
    ```

    ```json
    { "result": 84, "operation": "multiply", "operands": [6, 7, 2] }
    ```
  </Tab>
</Tabs>

## Differences

<AccordionGroup>
  <Accordion title="Request shape" defaultOpen>
    v1 sends `{ "a": 6, "b": 7 }`. v2 sends `{ "operation": "multiply", "operands": [6, 7] }`.
  </Accordion>
  <Accordion title="Response shape">
    v1 returns `{ "result": 42 }`. v2 returns the same field and also echoes `operation` and `operands`.
  </Accordion>
  <Accordion title="Errors">
    The same in both: dividing by zero returns a `400` with a `detail` message.
  </Accordion>
</AccordionGroup>

<Info>
  A real API would version through a header or a path prefix and keep old versions working. This demo uses the path prefix (`/v1`, `/v2`) so each version shows up as its own group in the API reference.
</Info>

## Migrating from v1 to v2

<Steps>
  <Step title="Change the URL">
    Replace `/v1/<operation>` with `/v2/calculate`.
  </Step>
  <Step title="Change the body">
    Move the operation name into the body and put your numbers in `operands`.
  </Step>
  <Step title="Read the same result">
    The `result` field works the same way.
  </Step>
</Steps>
